# Tunnel AI 工作规则

## 工作方式

- 用户的当前要求和会话中已有授权优先。直接完成已授权的修改，不为同一动作反复确认。
- 开始时读项目入口和项目记忆，检查 Git 状态，再定位相关源码。不要通读所有文档或重复扫描无关模块。
- 在工作区开发，保留用户及其他任务已有修改；禁止用 reset、clean 等方式丢弃它们。
- Git 提交、推送和发布按用户授权执行。普通修复不自动扩展为部署、生产操作或凭据变更。
- Android / Windows 完整编译在用户的正式构建服务器进行。本地可做源码、差异和文档引用检查，不擅自安装工具链或执行产品构建。
- 修改控制链要检查 Dart → Rust → 协议 → JNI → Kotlin 的相关路径；生成文件先找生成源。

## 文档从简

- 不要求每任务建文档、登记编号、生成审计/交接报告或维护事件流水。
- 不恢复已取消的多份状态表、历史表、决定日志和任务模板。
- 一般代码修复只需代码与必要验证，最终答复简述结果即可。
- 使用方式、接口、架构或构建步骤改变时，更新对应的一份主要文档。
- 长期重要约定集中在 `.codex/PROJECT_MEMORY.md`；变更历史交给 Git。
- 外部二进制的来源、版本、哈希和许可需要保存，不能作为无用文档删除。
- 保留第三方许可证、版权与必要使用说明。

## 工程约束

- 源码是实现真相；计划、静态检查、编译和真机验证必须区分，不能声称未执行的测试通过。
- Android core service、screen share、frame source、PC waiting 分开管理。
- 只有显式用户操作可请求新 MediaProjection 授权；重连和等待首帧不能自动切无视或截屏。
- JNI 以 `pkg2230.rs` 为主，修改时检查 `ffi.rs` 兼容路径。
- Controller 保持 relay-only；协议变更保留旧字段编号与授权检查。
- ADB 控制必须经过会话授权；配对码不进日志、持久配置或命令行参数。
- timer、subscription、native buffer 与 helper 必须有明确所属会话和释放路径。
- 不输出凭据、Token、私钥或个人信息；发现风险只报告位置和影响，不试用凭据。
- 不推断仓库外 backend、数据库、hbbs/hbbr 或签名服务已被验证。
